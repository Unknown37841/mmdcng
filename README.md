# Sub Merger + Health Checker (VLESS)

این پروژه چند تا ساب لینک VLESS رو می‌گیره، سلامت هر کانفیگ رو تست می‌کنه، و یک
ساب خروجی می‌سازه که فقط شامل سریع‌ترین و سالم‌ترین کانفیگ‌هاست.

## منطق کار
1. هر ساب ورودی از `subs.txt` خونده و دانلود میشه.
2. محتوای هر ساب (base64) دیکد میشه و کانفیگ‌های `vless://` استخراج میشن.
3. برای هر کانفیگ، یک اتصال TCP خام به `host:port` تست میشه و تاخیر (ping) اندازه‌گیری میشه.
4. اگر **همه‌ی** کانفیگ‌های یک ساب قطع بودن → کل اون ساب از خروجی حذف میشه.
5. اگر بخشی از کانفیگ‌ها زنده بودن → فقط `TOP_N` (پیش‌فرض ۳) تا سریع‌ترین از همون ساب نگه داشته میشه.
6. نتیجه‌ی نهایی (ترکیب همه‌ی ساب‌های زنده) به صورت base64 در `output_sub.txt` نوشته میشه.
7. یک گزارش خوانا هم در `report.txt` ذخیره میشه (چه سابی حذف شد، چند تا کانفیگ از هرکدوم زنده بود).

> نکته مهم: تست فعلی فقط "باز بودن پورت روی سرور" رو چک می‌کنه (TCP connect)،
> نه هندشیک کامل VLESS. این کار عمداً اینطوریه تا بدون نصب هیچ باینری اضافه‌ای
> (مثل xray-core) روی ران‌رهای رایگان گیت‌هاب اکشن اجرا بشه. اگر بعداً خواستی
> تست واقعی‌تر (هندشیک کامل TLS/Reality) داشته باشی، باید xray-core رو در
> ورک‌فلو نصب کنی و برای هر کانفیگ یک پراکسی موقت بالا بیاری و یک درخواست HTTP
> واقعی از توش رد کنی؛ کندتره ولی دقیق‌تره. بگو تا همون نسخه رو هم برات بسازم.

## راه‌اندازی (قدم به قدم)

1. یک ریپوی عمومی (public) جدید در گیت‌هاب بساز.
2. سه فایل زیر رو داخلش قرار بده (ساختار پوشه‌ها رو حفظ کن):
   - `check_and_build.py`
   - `subs.txt`
   - `.github/workflows/update.yml`
3. داخل `subs.txt` لینک ساب‌های خودت رو بذار (هر خط یک لینک، خطوط با # کامنت هستن).
4. برو تب **Settings > Actions > General** ریپو، و زیر «Workflow permissions»
   گزینه‌ی **Read and write permissions** رو فعال کن (تا ورک‌فلو بتونه commit/push کنه).
5. برو تب **Actions**، ورک‌فلوی «Update Subscription» رو پیدا کن و یک بار
   دستی (`Run workflow`) اجراش کن تا `output_sub.txt` اولیه ساخته بشه.
6. از اون به بعد هر ۳ ساعت یک‌بار خودکار اجرا میشه (میتونی زمان‌بندی `cron` رو
   در `update.yml` عوض کنی، مثلاً `0 */1 * * *` برای هر ساعت).

## آدرس ساب خروجی

بعد از اولین اجرا، لینک زیر همون ساب نهایی توئه (USERNAME و REPO رو عوض کن):

```
https://raw.githubusercontent.com/USERNAME/REPO/main/output_sub.txt
```

اگر `raw.githubusercontent.com` براتون فیلتر/کند بود، از آینه‌ی jsDelivr
استفاده کن که معمولاً سریع‌تر و در دسترس‌تره:

```
https://cdn.jsdelivr.net/gh/USERNAME/REPO@main/output_sub.txt
```
(توجه: jsDelivr کش داره، ممکنه چند دقیقه طول بکشه تا آپدیت جدید رو نشون بده.)

## تنظیمات (فایل config.json)

دیگه لازم نیست کد پایتون رو باز کنی؛ همه‌ی تنظیمات مهم تو فایل `config.json` هستن
و می‌تونی مستقیم توی گیت‌هاب (کلیک روی فایل → ✏️ → ویرایش → Commit) عوضشون کنی:

```json
{
  "top_n_per_sub": 3,
  "timeout_seconds": 5,
  "retries": 2,
  "max_workers": 20,
  "tag_configs_with_source": false
}
```

| کلید | توضیح |
|---|---|
| `top_n_per_sub` | چند تا کانفیگِ سریعِ سالم از هر ساب نگه داشته بشه (پیش‌فرض ۳) |
| `timeout_seconds` | حداکثر زمان انتظار برای هر تلاش اتصال (ثانیه) |
| `retries` | هر کانفیگ چند بار تست بشه (بهترین نتیجه نگه داشته می‌شه) |
| `max_workers` | چند تا کانفیگ همزمان (موازی) تست بشن — هرچی بیشتر، اجرا سریع‌تره ولی فشار بیشتری هم میاد |
| `tag_configs_with_source` | اگه `true` باشه، به اسم هر کانفیگِ خروجی می‌چسبونه که از کدوم ساب اومده (مثلاً `| sub3`)، برای دیباگ/شناسایی مفیده |

### override به‌ازای هر ساب (اختیاری)

اگه می‌خوای فقط یک ساب خاص عدد متفاوتی از `top_n_per_sub` عمومی داشته باشه،
تو `subs.txt` جلوی همون لینک با کاما عدد دلخواه رو بنویس:

```
https://example.com/sub1
https://example.com/sub2, 5
https://example.com/sub3, 1
```

تو مثال بالا: از `sub1` طبق تنظیم عمومی (۳ تا)، از `sub2` پنج‌تا، و از `sub3`
فقط یک‌دونه سریع‌ترین کانفیگ برداشته می‌شه.

## تست موازی (سریع‌تر شدن اجرا)

نسخه‌ی جدید همه‌ی کانفیگ‌های همه‌ی ساب‌ها رو با `ThreadPoolExecutor` به صورت
موازی تست می‌کنه (تعداد رشته‌ها با `max_workers` کنترل می‌شه)، نه یکی‌یکی.
این باعث می‌شه حتی با تعداد زیاد ساب/کانفیگ، هر اجرا در چند ثانیه تا چند
دقیقه تموم بشه و برای کرون هر ۳۰ دقیقه‌ای مشکلی پیش نیاد.

## تغییر بازه‌ی زمانیِ چک شدن ساب‌ها

بازه‌ی زمانی (چند وقت یک‌بار تست انجام بشه) توی خودِ فایل
`.github/workflows/update.yml` تنظیم می‌شه، نه `config.json` — چون گیت‌هاب
این زمان‌بندی رو قبل از اجرای هر کدی می‌خونه، پس نمی‌تونه از فایل تنظیمات
داخل پروژه بیاد. برای عوضش، بالای همون فایل یک جدول از الگوهای آماده هست؛
کافیه خط `cron` رو با یکی از این‌ها جایگزین کنی (وقت‌ها بر پایه‌ی UTC هستن):

| بازه | مقدار cron |
|---|---|
| هر ۱۵ دقیقه | `*/15 * * * *` |
| هر ۳۰ دقیقه (پیش‌فرض) | `*/30 * * * *` |
| هر ۱ ساعت | `0 * * * *` |
| هر ۳ ساعت | `0 */3 * * *` |
| هر ۶ ساعت | `0 */6 * * *` |
| یک‌بار در روز | `0 3 * * *` |

بعد از عوض کردن، فقط کافیه commit کنی؛ از اجرای بعدی همون بازه‌ی جدید اعمال می‌شه.

## اجرای دستی با override موقت

از تب **Actions**، اگه ورک‌فلو رو با دکمه‌ی **Run workflow** دستی اجرا کنی، یک
فیلد اختیاری به اسم `top_n_override` می‌بینی. اگه توش عددی بدی (مثلاً `5`)،
فقط برای همون یک اجرا مقدار `top_n_per_sub` رو نادیده می‌گیره — برای تست سریع
بدون اینکه لازم باشه `config.json` رو موقتاً عوض کنی و بعد برگردونی.

## رفع محدودیت ۶۰ روزه (غیرفعال شدن خودکار ورک‌فلوی زمان‌بندی‌شده)

گیت‌هاب هر ورک‌فلوی زمان‌بندی‌شده (schedule) رو تو ریپوهای عمومی، اگه **۶۰ روز
پشت‌سرهم هیچ commit واقعی** روی ریپو ثبت نشه، خودکار خاموش می‌کنه. نکته‌ی مهم:
فقط commit واقعی حساب می‌شه، نه اجرای خودِ ورک‌فلو یا باز شدن issue/PR.

راه‌حلی که تو این نسخه اضافه شده: اسکریپت هر بار یک فایل کوچیک به اسم
`last_checked.txt` (شامل تاریخ/ساعت آخرین اجرا و خلاصه‌ی نتیجه) می‌سازه که
**هر بار محتواش عوض می‌شه**، پس هر اجرا یک commit واقعی و تازه ثبت می‌کنه —
یعنی ریپو هیچ‌وقت «بی‌فعالیت» به حساب نمیاد و لازم نیست هیچ کار دستی‌ای انجام
بدی یا اکشن سوم‌شخصی نصب کنی. تنها نکته: اگه یک روز تصمیم گرفتی خودِ ورک‌فلو
رو موقتاً از تب Actions دستی خاموش (Disable) کنی، طبیعتاً دیگه هیچ commit ای
هم ثبت نمی‌شه و بعد از ۶۰ روز اگه دوباره Enable ش کنی باید همین‌طوری غیرفعال
نمونه.

## چند تنظیم پیشنهادی دیگه (که می‌تونی بعداً اضافه کنی، بگو تا برات پیاده کنم)

- **حداقل درصد سلامت به‌جای «حداقل یک کانفیگ زنده»** — مثلاً اگه کمتر از ۲۰٪
  کانفیگ‌های یک ساب زنده بودن، اون ساب مشکوک به تعطیلی حساب بشه و کلاً حذف
  بشه (نه اینکه با همون یکی-دوتا نگه داشته بشه).
- **هشدار Telegram/Discord** — وقتی یک ساب کامل dropped می‌شه، یک پیام
  خودکار به ربات تلگرام یا وبهوک دیسکورد بفرسته تا فوری بفهمی کدوم منبع
  از کار افتاده.
- **آرشیو تاریخچه‌ی latency** — هر اجرا نتایج رو تو یک فایل CSV اضافه کنه
  تا بعداً بتونی نمودار بگیری ببینی کدوم ساب پایدارتره.
- **حذف کانفیگ‌های تکراری بر اساس IP:port** (نه اسم) — اگه دو تا ساب از یک
  سرور فیزیکی استفاده می‌کنن، فقط سریع‌ترینش تو خروجی بمونه.
- **چند خروجی جدا به‌جای یکی** — مثلاً یک ساب فقط برای موبایل (کانفیگ‌های
  کم‌مصرف‌تر) و یکی برای دسکتاپ، بر اساس تگ‌گذاری کانفیگ‌ها.


## محدودیت‌های نسخه رایگان گیت‌هاب اکشن

- برای ریپوی **public** دقیقه‌های اجرای رایگان عملاً نامحدوده (فقط سقف‌های نرم
  استفاده‌ی منصفانه‌ی گیت‌هاب رو رعایت کن، مثلاً هر اجرا رو خیلی کوتاه نگه دار).
- کران گیت‌هاب اکشن گارانتی دقیقه‌به‌دقیقه نیست؛ با بار ۳۰ دقیقه‌ای ممکنه گاهی
  چند دقیقه دیرتر اجرا بشه، طبیعیه.
- ⚠️ گیت‌هاب به صورت خودکار **scheduled workflow ها رو بعد از ۶۰ روز عدم فعالیت
  ریپو (بدون هیچ commit) غیرفعال می‌کنه**. چون این پروژه با هر اجرا خودش commit
  می‌زنه (وقتی خروجی تغییر کنه) معمولاً مشکلی پیش نمیاد، ولی اگه یک مدت طولانی
  همه‌ی سرورها زنده بودن و خروجی عوض نشد، ممکنه لازم بشه یک بار دستی از تب
  Actions اجراش کنی.
- تعداد ساب‌های داخل `subs.txt` هیچ محدودیتی نداره؛ هر خط یک ساب اضافه‌ست، فقط
  هرچی تعداد بیشتر باشه، هر اجرا کمی بیشتر طول می‌کشه (چون تست‌ها به‌ترتیب انجام می‌شن).

## درباره‌ی روش تست (چرا فقط TCP کافی نبود)

خیلی از کانفیگ‌های VLESS پشت CDN مثل کلادفلر هستن (مثل نمونه‌ای که با
`type=ws&security=tls` و آدرس IP کلادفلر مشخصه). در این حالت آدرس سرور یک IP
عمومی و اشتراکی کلادفلره که تقریباً همیشه در دسترسه، حتی اگه ورکر یا توکن پشتش
از کار افتاده باشه. برای همین این اسکریپت به جای یک TCP connect ساده، یک
**درخواست واقعی WebSocket Upgrade** (با TLS + SNI + Host + Path درست) می‌فرسته
و فقط جوابِ `HTTP 101 Switching Protocols` رو «زنده» حساب می‌کنه. برای انواع
دیگه‌ی transport (تی‌سی‌پی ساده، gRPC و...) فعلاً همون TCP(+TLS) connect به
عنوان تست پایه استفاده می‌شه.
